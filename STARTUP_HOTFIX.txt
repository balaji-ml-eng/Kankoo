APK signature verification and 16 KB native-library ZIP alignment check passed.
Architecture validation FAILED: the APK contains helper libraries under
armeabi-v7a and x86_64, so Android advertises those ABIs, but neither includes
libflutter.so, libapp.so or libsqlcipher.so. Only arm64-v8a is complete. Thus a
32-bit ARM or x86_64 device can install an APK that cannot load its Flutter app.
The original ARM64 filename did not prevent this packaging defect.
The hotfix is built as a universal release with all three core ABI sets, rather
than building ARM64 Flutter code into an APK that still contains other ABIs.

Confirmed source problem; device-specific cause not yet confirmed
The published main() waits for SharedPreferences.getInstance(), then awaits
FlutterEdgeAi.initialize() and FileDownloader.cancelAll(), before calling runApp().
The optional AI/download waits had no timeout. Catching an exception does not
handle a future that never completes. That code path can leave Android's native
splash visible forever because Flutter has not rendered its first frame.
Both issues can cause startup failure. No physical device is connected to adb
here, so the exact cause on the user's phone is not yet proven. Its CPU ABI and
a device startup log are required if the corrected universal APK still sticks.

Changes
lib/main.dart: calls runApp immediately, before any asynchronous plugin wait.
lib/core/startup_gate.dart: paints an opening screen while saved settings load;
after 10 seconds a failed/stalled settings load shows Retry instead of staying on
the native splash. It never substitutes empty preferences or bypasses app lock.
The real app is mounted only with its existing saved settings. Optional services
start after the app's ready frame, and cannot gate first paint or normal taps.
lib/llm/on_device/on_device_initialization.dart: shares one AI initialization
future between startup/settings/clients, with a 15-second caller timeout. A late
native future is retained so retries cannot start competing initializations.
lib/llm/on_device/on_device_client.dart: waits for that shared initialization;
attaches lifecycle cleanup when an AI model is actually loaded, including after
a delayed initialization. Cloud AI behavior is unchanged.
lib/llm/on_device/on_device_models.dart: bounds orphan download cleanup to five
seconds and waits for AI readiness when refreshing the model screen.
test/startup_gate_test.dart: regression tests for hung optional services, their
failures, hung critical settings, safe retry and late completion after disposal.
tool/verify_apk_architectures.py: rejects an APK if ANY advertised native ABI lacks
its Flutter engine, compiled app or SQLCipher. It reproduces the old APK failure.
Build command: flutter build apk --release --no-pub (default complete ABI set).
.github/workflows/build-apk.yml: builds a complete debug APK and runs the same
architecture check before publishing its CI artifact. Signed releases still use
the protected release key and are not replaced by CI debug artifacts.
pubspec.yaml: 1.0.3+7, a version code higher than the published APK.

There are no database schema, transaction parser, invoice, milestone, key storage
or authentication-policy changes. This hotfix remains on the released schema 4.
It does not delete preferences, replace encryption keys or reset app data.

Phone verification
The corrected APK is intended to update the signed 1.0.2 installation in place.
Do not uninstall or clear storage: that would remove local data/device-bound keys.
If it reaches 'Opening Kankoo' or the settings Retry screen, Dart/Flutter first
paint is working; the native splash has been passed. If it still shows only the
Android splash/logo, capture startup logcat to investigate native engine/renderer
or phone-specific startup failure. The app emits only startup stage markers and
error types under [kankoo-startup], without settings or transaction contents.
Physical testing on the user's phone remains pending. The publishing target is
GitHub tag v1.0.3-test, from main, with the universal signed APK described above.
